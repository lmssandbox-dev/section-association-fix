# Project guide

Brightspace Section Association Fix is a Node.js 22 service that discovers IPSIS Section Association Course Offerings, resolves grouped sections to original standalone Course Offerings, and inactivates those originals.

## Architecture

- `index.js` composes web configuration, optional LTI setup, and trigger mode.
- `src/shared/` contains service-account OAuth, HTTPS/API transport, Mongo URL validation, and shared rate limiting.
- `src/sectionAssociations/` contains discovery, resolution, validation, persistence, scheduling, and one reconciliation engine shared by cron and internal modes.
- The recurring Section Association Fix worker is the production processing path; historical baseline records are included in its bounded work selection.

The worker uses only the Brightspace OAuth service account. LTI is not required for reconciliation. When LTI registration is configured, the launch page provides a compact authenticated status view and the administrator-only Run Now trigger.

## Trigger modes

`SECTION_ASSOCIATION_FIX_TRIGGER_MODE=cron` is the default for sleeping web services. Use the existing single Render Cron Job on `*/15 * * * *` with `npm run cron:section-association`; it runs 24/7 and gates work using `America/Sao_Paulo`. Period discovery and direct-child monitoring run 07:00–23:00; broad historical discovery runs once per logical 23:00–01:00 nightly window; its window key is the date on which 23:00 began, so success before midnight prevents a duplicate after midnight and failures retry within the window; cached-ID status verification runs every 30 minutes at :00 and :30 from 01:00 through 06:30. Pending and blocked recovery stays eligible 24 hours a day. `SECTION_ASSOCIATION_DISCOVERY_PERIODS` unset, empty, or `auto` searches previous/current/next; comma-separated `YY01`/`YY02` values search exactly those periods; `all` performs daily broad discovery while ongoing monitoring remains previous/current/next. New records keep the 10-minute stability delay. Child and status checks default to 125 and 150 associations per eligible invocation, have separate configuration, and share the Brightspace limiter. Fast and recovery work share the limit of 50 full reconciliations per invocation. Cron and internal runs share the Mongo lease and reconciliation engine. Existing validation, dry-run, and verified-write safety rules apply.

Use `internal` only on always-on hosting; it starts an immediate fast cycle and recurring fast/recovery timers. Both modes share the same Mongo lease, service, and reconciliation engine. Never run the external cron while internal timers are active.

The LTI dashboard Run Now action is administrator-only and uses the same one-shot cron controller, service, lease, API limiter, and 50-reconciliation cap in either trigger mode. It always performs fresh period-scoped discovery, including outside daytime hours, using the explicit configured periods or previous/current/next when scope is auto, unset, or all. It never triggers broad historical discovery solely because it is manual. Newly discovered records retain the 10-minute stability delay; child monitoring and cached-status verification remain gated by their normal windows. The action creates one tenant-scoped durable manual request, dispatches asynchronously, and reports requested/running/completed/failed state from Mongo. The web process retries active requests every 30 seconds; automatic cron invocations and internal-mode polling can recover requested or interrupted requests after restart. The lease must be acquired before the request is marked running. A request is rejected unless the validated LTI roles claim explicitly contains Administrator or SysAdmin. Do not add new environment settings for Run Now.

## Eligibility and status

Academic periods use the `America/Sao_Paulo` calendar: January–June is `YY01`; July–December is `YY02`. Automatic scope covers previous/current/next (October 2026: `2601`, `2602`, `2701`). Since October 30, 2026, associations use two exclusive code families: legacy `002521-01-2602-I0001` and PeopleSoft `ESPM-2602-GS2-C0011`. For each selected period, discovery makes the substring searches `{period}-I0001` and `ESPM-{period}-`; no session or sequence values are configured. A successful pair of broad `I0001` and `ESPM-` scans is timestamped in tenant-scoped Mongo metadata and runs once per logical 23:00–01:00 local nightly window; its key is the date on which 23:00 began, so success before midnight prevents a duplicate scan after midnight and failures retry within the window. It preserves historical and future-period coverage without querying every historical association every 15 minutes. In `all` mode, broad searches run once daily; ongoing monitoring uses previous/current/next. Discovery can only find offerings successfully created in Brightspace; a broader period scope does not repair failed IPSIS imports. `baseline: true` is audit metadata and never permanently excludes a valid association. New associations wait the configured stability window (default ten minutes); historical baseline records do not. Full reconciliation saves a versioned verified child/target snapshot. Daytime monitoring compares child IDs and Org Codes; nighttime checks cached original IDs, which never independently authorize writes. Pending and blocked recovery work continues throughout the day. A single initial association-detail HTTP 404 records `missingObservedAt` while the association remains pending. The service marks it `missing` only after 30 minutes and a newer successful discovery of the same code family and academic period (or a successful broad scan of that family) omits the exact D2L ID. Results from the other format, failed/partial queries, and stale results cannot confirm absence. Missing records remain in Mongo for history, are excluded from fast and recovery work, and add a `missing-confirmed` Exceptions CSV lifecycle row without counting as completed or corrected. Same-ID discovery restores pending status and clears missing metadata; a different ID with the same Org Code remains an independent record. No Recycle Bin request is used. `lastSeenAt` advances only on positive discovery; `lastCheckedAt` tracks reconciliation attempts. Legacy records need no migration: absent missing metadata means no potential-missing observation.

Every association requires a Course Offering with either the strict legacy code pattern `^\\d{6}-\\d{2}-\\d{4}-I0001$` or the PeopleSoft shape `ESPM-{valid YY01/YY02 period}-{nonblank remainder}`, at least one direct Group child, valid five-digit child suffixes, and exactly one distinct Course Offering for every derived code. Validate all targets before writing. Inactive targets are no-ops. The only Brightspace mutation is a full Course Offering PUT changing `IsActive` from true to false, followed by verification. Never replay an uncertain write.

Successful full reconciliation stores a versioned snapshot of child IDs/codes and corresponding original Course Offering IDs/codes, with separate successful child-inspection and cached-status-verification timestamps. A completed dry run may persist this snapshot only after fresh reads confirm all targets are already inactive; dry-run active targets remain pending without a completed mapping. Expanded Execution History details show checks, changes, mapping refreshes, and remaining monitoring backlog only for activities actually performed and recorded. Daytime child monitoring runs 07:00–23:00 and nighttime cached-ID status reads run every 30 minutes at :00 and :30 from 01:00 through 06:30. Cached IDs never authorize a PUT: an active, missing, or inconsistent target must pass fresh structural validation and the normal safe reconciler. Missing snapshots are populated through full reconciliation. Dry-run is the default and sends zero PUTs. If active targets remain, keep the record pending for later live processing. Do not change OAuth, LTI, association rules, or scheduler intervals without explicit task scope.

`SECTION_ASSOCIATION_DEBUG_ID` is an optional, temporary diagnostic setting for one numeric association ID, or `sample` to log the first association inspected by daytime child monitoring in each execution. It logs saved/current child IDs and Org Codes, child types, mapping trust/comparison results, reconciliation reason and capacity disposition, and whether successful inspection time advanced. It adds no reads and does not alter processing. Keep it unset normally and remove it after troubleshooting.

Reconciliation failures use stable diagnostic stages: `association-read`, `children-read`, `exact-code-lookup`, `target-read`, `target-update`, and `verification-read`. Render logs include the stage, safe endpoint identifier, stable reason, and HTTP status when known; they never include raw response data or request URLs. Timeout, network, and OAuth failures are identified when reliable evidence exists. Exceptions CSV categories distinguish `read-failed`, `update-failed`, `verification-failed`, `validation-blocked`, and `processing-error`; explanations include the failed operation and available status or target Org Code/ID. Operators can find these details in the Exceptions CSV for an execution; expanded Execution History uses the existing persisted run summary.

Discovery persistence compares valid, distinct association IDs against the tenant-scoped `section_associations` collection in batches of 500. Only IDs missing from the comparison are upserted with `$setOnInsert`; already-known records are refreshed in bounded bulk writes so discovery-only `lastSeenAt` retains its operational meaning without per-association round trips. Reconciliation writes update `lastCheckedAt` without advancing `lastSeenAt`. Discovery and baseline bulk operations are bounded, counters count distinct valid association IDs, duplicate-key races are handled idempotently, and partial database failures must fail the cycle.

## LTI interface

The LTI launch page is a compact monitor with Service Status, API Health Check, Execution History, and an administrator-only Run Now action. Run Now is protected by validated LTI session, deployment, same-origin, and administrator-role checks. API Health Check runs in-page, displays cached tenant assessment results, and offers a protected manual check. It uses its own tenant-scoped persistence and coordination; health failures must not affect reconciliation or maintenance history. Its 36-hour stale threshold, five-minute manual cooldown, and 30-success history limit are fixed. Lifecycle evidence is dated and must be maintained with the endpoint inventory; unknown or stale evidence cannot be reported Healthy. Keep Version Health separate from Contract Verification. The endpoint inventory, source coverage tests, and documentation must be updated for any Brightspace method, route, version setting, OAuth scope, or contract change.

The Service Status view groups availability and worker state, shows the configured discovery period codes in bold or “All periods”, and presents the latest date and outcome. It omits the redundant Source field and suppresses a zero-work message already evident from the history counts. Execution History displays 50 records per page with Previous/Next controls and optional inclusive From/To filters on execution start dates, interpreted in `America/Sao_Paulo`; users can navigate all retained executions. At wide widths, history uses six aligned columns for date, `Periods / Scope`, outcome, and counts. Responsive layouts use history-container queries at 720px and 560px, with viewport media-query fallbacks at 860px and 620px: medium rows use two lines (date/outcome, then scope and labeled counters); narrow rows stack date/outcome, scope, and a three-column count grid. On narrow screens, date filters stack both inputs above the Apply/Clear pair and Service Status stacks. Desktop rows have 20px vertical summary padding; outcome badges are centered in their column and numeric counts are right-aligned and locale-formatted. Rows show the actual configured/resolved scope when recorded, plus `Mixed` when period discovery was combined with other activity. Historical-only and re-verification-only rows use those labels; missing or old metadata shows `—`. Expanded rows use a padded compact strip without repeating scope already shown in the row: successful zero-work runs show “No work required” and duration; processed runs show Already compliant and duration; failed/incomplete runs show available duration and an existing explanation. An accessible Reports dropdown offers Corrections CSV and Exceptions CSV when detailed auditing is available; older runs show a short unavailable message. Refresh preserves filters and page; Export History CSV always includes every retained execution, independent of filters and pagination, and preserves its existing columns and contents. No retention or automatic deletion policy is applied. Feedback is transient on success and remains accessible for errors. Execution summaries are stored as one idempotently upserted document per execution in tenant-scoped `section_association_meta`; discovery metadata records only completed period queries and activities actually performed. Detailed rows are separate documents in `section_association_audit`, uniquely indexed by namespace, execution ID, kind, and stable record key, with a retrieval index by namespace, execution ID, and kind. No TTL or count-based pruning is applied. Corrections record only actual read-back-verified state changes; the aggregate correction counter remains association-level. Exceptions distinguish validation blocks, failed updates, failed verification, and unexpected failures; exception row counts do not define aggregate errors. Both audit exports require the verified LTI session and configured deployment ID. CSV output is generated from MongoDB on demand, escapes CSV and spreadsheet formulas, and does not call Brightspace. Automatic and manual execution are covered. Historical runs without `detailedAuditAvailable: true` have no verified detail coverage and are not exported as zero activity. Indexes are created automatically at store initialization; no data migration is required. Do not add corrective operations without separate backend authorization and support.

## Development

Run `npm test` and `npm run check`. Keep real secrets out of source control. See `README.md`, `ENVIRONMENT.md`, and `TECHNICAL.md` for configuration and operations.

## Brightspace API inventory maintenance

Any future change to a Brightspace API endpoint, HTTP method, version setting, OAuth scope, or request/response contract must update `src/sectionAssociations/apiHealthInventory.js`, the inventory source-coverage tests, and relevant documentation. Keep lifecycle statements dated and supported by official D2L references; leave unsupported minimums or contract claims Unknown or Not Verified.
