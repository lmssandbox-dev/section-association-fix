# Brightspace Section Association Fix

This service detects Course Offerings created by IPSIS Section Association processing and inactivates the original standalone Course Offerings represented by their grouped sections. It does not rename or delete anything, move groups, or change enrollments or mappings.

## How it works

Every 15 minutes the worker searches the configured academic-period scope. `SECTION_ASSOCIATION_DISCOVERY_PERIODS` unset, empty, or set to `auto` searches previous, current, and next periods. Periods use the `America/Sao_Paulo` calendar: `YY01` means January–June and `YY02` means July–December. In October 2026, automatic discovery searches `2601`, `2602`, and `2701`. A comma-separated value such as `2601,2602,2701` or a single value such as `2701` searches exactly those periods. Set the variable to `all` to search every period during each fast cycle. Values are trimmed, duplicate periods removed, and invalid values fail startup.

In Render, configure automatic discovery by removing `SECTION_ASSOCIATION_DISCOVERY_PERIODS`, leaving it empty, or setting it to `auto`. Configure all-period discovery with `all`. Regular period queries use `orgUnitCode={period}-I0001`; the separate broad `orgUnitCode=I0001` scan covers historical and future associations once daily after 02:00 local time for auto and explicit scopes, and initializes the first baseline. In `all` mode, the regular broad query also serves as the full scan, avoiding a duplicate request. Period selection only changes which existing Brightspace offerings are searched; it cannot make an association appear if its IPSIS import failed to create it successfully in Brightspace. All queries follow Brightspace pagination and apply the same exact association-code validation. Each valid association must be a Course Offering with at least one direct Group child; each child code must end in a hyphen and exactly five digits. Removing that suffix produces an original Course Offering code that must resolve to exactly one Course Offering.

Discovery persistence compares distinct valid association IDs with the tenant-scoped Mongo collection in batches of 500. Existing records are refreshed in bounded bulk writes to preserve discovery-only `lastSeenAt`; only IDs not found are inserted using `$setOnInsert`, preserving existing reconciliation state and baseline metadata. Reconciliation attempts update `lastCheckedAt`, not `lastSeenAt`. Bulk writes are bounded, duplicate-key races remain idempotent, and partial database failures fail the cycle.

If an association-detail GET returns HTTP 404, the ledger records a potential-missing timestamp and keeps the association pending. It becomes `missing` only after 30 minutes and a later successful discovery for its academic period (or a broad `I0001` scan) omits that exact Org Unit ID. Failed, incomplete, stale, or unrelated queries do not establish absence, and no Recycle Bin API call is made. Missing records stay in Mongo history and leave fast/recovery queues. Discovery of the same ID restores pending processing and clears missing metadata; the same Org Code under another ID remains a separate record. Render logs show the observation, confirmation, and restoration events. Exceptions CSV includes the initial read failure and one `missing-confirmed` lifecycle row; missing status is not counted as completed or corrected. Legacy records require no migration.

The worker validates the complete target set before writing. It re-reads each current Course Offering, skips already-inactive records, and only changes `IsActive` to `false` through a full PUT followed by a verification GET. Dry-run performs the same discovery and validation but sends no PUTs; active targets stay pending for later live processing.

## Unified processing and safety

The first successful discovery records the current association population with `baseline: true` for audit history. Baseline status does not permanently exclude an association: historical and new records use the same reconciler. Historical records do not wait through the new-association stability window. New records wait `SECTION_ASSOCIATION_FIX_STABILITY_MINUTES` (default 10).

Each scheduled run handles at most `SECTION_ASSOCIATION_FIX_MAX_RECONCILIATIONS_PER_RUN` associations (default 50), prioritizing new and pending work, then historical records, then controlled blocked retries. Previously completed records without positive verification evidence are eligible automatically. Verified completed associations become eligible every `SECTION_ASSOCIATION_FIX_COMPLETED_REVERIFY_HOURS` (default 24), and are re-read only from 03:00 through 06:00 America/Sao_Paulo. Backlogs resume in later maintenance windows. If a target is active again, it is reconciled through the normal validation and update path.

Dry-run and live processing share the same engine. Every target is checked before the first write. The only mutation is Course Offering `IsActive: true` to `false`; uncertain writes are read back and never blindly replayed. MongoDB is an operational work ledger, not proof of Brightspace state.

## Authentication

Background calls use Brightspace Server-to-Server OAuth 2.0 client credentials with a signed private-key JWT. LTI 1.3 registration is optional at startup and is unrelated to worker authentication. The service account needs `organizations:organization:read` and `orgunits:course:update`, plus Brightspace organizational-structure read access and Manage Courses permission.

## Hosting / Trigger Modes

`SECTION_ASSOCIATION_FIX_TRIGGER_MODE=cron` is the default for Render Free and other sleeping web services. Configure one Render Cron Job from this repository on `*/15 * * * *` with command `npm run cron:section-association`. Each invocation performs bounded period discovery and runs non-completed recovery when its independent four-hour schedule is due. Nightly full discovery and completed-association verification use the same cron job; no additional job is needed.

### Daily schedule at a glance

| Work | Timing | Discovery or processing |
| --- | --- | --- |
| Fast discovery | Every 15 minutes | Configured scope; auto October 2026 uses `2601-I0001`, `2602-I0001`, and `2701-I0001`; `all` uses one broad `I0001` query. |
| Full discovery | Initial baseline, then once daily at or after 02:00 `America/Sao_Paulo` | Broad `I0001` query covers historical and future periods for auto/explicit modes. In `all` mode the fast query also satisfies full discovery. If missed or unsuccessful, the next cron invocation retries it. |
| Completed re-verification | 03:00–06:00 `America/Sao_Paulo` | Only completed associations at least 24 hours past successful verification are eligible. |
| Recovery | Every four hours | Pending and retryable blocked work remains eligible throughout the day. |

Automatic mode searches three adjacent periods. A deployment can narrow or expand regular discovery with `SECTION_ASSOCIATION_DISCOVERY_PERIODS`; the daily broad scan still finds associations in any past or future period for auto and explicit scopes, preserving historical coverage without repeating the broad Brightspace read every 15 minutes. Periods roll over automatically, so no manual academic-period maintenance or second cron job is needed.

Cron and the worker use a namespaced Mongo lease. It is renewed during work and explicitly released after success or failure; expiry is crash protection. Run `npm run section-association:lease-status` to inspect its state without modifying MongoDB.

Set `SECTION_ASSOCIATION_FIX_TRIGGER_MODE=internal` only on always-on hosting. The web process starts an immediate fast cycle and recurring fast/recovery timers. Cron and internal runs coordinate through the same Mongo lease, service, and reconciliation engine.

## LTI bootstrap

Deploy first with the `BS_LTI_*` settings empty. The application starts in LTI setup mode, runs the Section Association worker, and serves `/ping` and `/.well-known/brightspace-jwks.json`. Register the tool in Brightspace using the public application keyset URL `https://<your-render-service>.onrender.com/.well-known/brightspace-jwks.json` (or the equivalent configured public domain). Then add the returned LTI Client ID and Deployment ID, plus all required platform endpoints, and redeploy. LTI launches are enabled after the complete configuration is present.

## LTI status page

An authenticated Brightspace launch opens a compact read-only monitor. Service Status groups availability and worker state, shows the actual discovery period codes in bold or “All periods”, and presents the latest date and outcome; it omits a zero-work message already evident from the history counts. It does not show execution source. History uses aligned date, **Periods / Scope**, outcome, and right-aligned count columns; counts use locale-aware grouping. Rows show the scope recorded for that execution, and append `Mixed` when discovery ran alongside other activities. Historical-only and re-verification-only runs use those labels; missing metadata displays `—`. Responsive history uses container-query breakpoints at 720px and 560px, with viewport fallbacks at 860px and 620px. Medium rows use date/outcome above scope and counters; narrow rows stack date/outcome, scope, then the three counts. Narrow date filters stack From and To inputs over adjacent Apply and Clear buttons, and Service Status stacks its fields. Desktop execution rows use 20px vertical summary padding. Expanded rows show concise work information and duration, concise failures, and the keyboard-accessible Reports dropdown without repeating scope shown in the row. Successful zero-work runs show “No work required” and duration. The page omits execution IDs, coverage, and historical backlog; those remain in stored summaries and CSV exports. Export feedback clears after success and announces errors accessibly. Refresh and Export History CSV are the page-level actions. To run the existing one-shot process as manual maintenance, use `node scripts/run-section-association.js --manual`; without that flag (including the configured Render cron command), the source remains recorded as automatic.

Execution History displays 50 records per page and Previous/Next controls navigate all retained executions. Optional From and To filters use inclusive calendar dates in `America/Sao_Paulo` and match execution start dates; changing filters resets to page 1. Refresh preserves the selected filters and current page. Export History CSV remains a complete, unfiltered export independent of the page and filters. No retention or automatic deletion policy has been introduced.

Summary counters count associations, not target writes: checked counts reconciliation attempts; already compliant counts associations whose resolved targets were all already inactive; corrections applied counts associations with one or more verified target updates; errors count failed association outcomes and known execution-level failures. Execution summaries persist the configured or resolved discovery scope and only activities that actually ran. Period query evidence is recorded after all configured period queries complete; historical discovery is recorded only after the broad query succeeds; re-verification is recorded when such a work item is processed. Older records remain unchanged and display `Not recorded`. Coverage contains the historical backlog count only when the worker returned it; this bounded-cycle value does not establish full-scan completion. If there is no execution, the page shows “No maintenance execution recorded yet.” Automatic and manual summaries are stored as one document per execution ID in the tenant-scoped `section_association_meta` collection. Writes are idempotent by execution ID; history has no count-based pruning or TTL, and is retained subject to MongoDB capacity and operational storage policy. Store initialization creates the `{ namespace: 1, history: 1, startedAt: -1, executionId: -1 }` index; no migration is required. Existing documents remain available, but records already deleted by the previous five-entry pruning cannot be reconstructed. Download CSV streams all retained execution summaries on demand, including records beyond the 50 shown in the page. Its existing columns (including execution ID and source) are preserved; discovery period identifiers and activities are appended. Missing stored values are blank; the CSV is not persisted. Both status and CSV endpoints require a validated LTI session and matching configured deployment ID, and responses are not cached. The browser sends the launch-generated ltijs token as a Bearer token plus same-origin credentials, which ltijs validates along with its session cookie; a 401 requires a fresh Brightspace launch.

### API Health Check

The Service Status heading has an **API Health Check** button. It opens an in-page view with the configured `D2L_API_LP_VERSION`, latest LP version supported by the tenant, current version health, endpoint risk counts, the last successful assessment, and evidence freshness. **Run Check** performs the diagnostic; **Endpoint Details** expands the inventory and official D2L references. Dashboard refreshes, page navigation, and opening the health view read MongoDB only.

The inventory in `src/sectionAssociations/apiHealthInventory.js` covers six logical operations across five method/route shapes. It tracks OAuth token exchange separately as an authentication diagnostic. Lifecycle evidence was checked on 2026-10-19 against the D2L developer documentation. Documented minimums are LP 1.49 for the Org Unit and Course Offering routes, and LP 1.59 for Course Offering updates that use `IsActive`. D2L does not document additional contract verification specific to this application's payloads; these entries remain **Not Verified**. Update the inventory, coverage tests, and documentation whenever Brightspace methods, routes, versions, scopes, or contracts change.

Version health checks tenant support with `GET /d2l/api/lp/versions/` and `POST /d2l/api/versions/check`, then applies the dated lifecycle evidence. Healthy means the configured version is tenant-supported, lifecycle evidence is current, and no documented risk applies. Update Available means a newer version is supported. At Risk means D2L marks the contract deprecated. Critical means it is unsupported, obsolete, or below a documented endpoint minimum. Unknown means the check failed or evidence is missing, stale, or incomplete. Contract Verification is shown separately and does not turn an otherwise supported version Unknown.

Cron mode starts a due daily assessment from the existing 15-minute invocation after reconciliation and its history have been saved, after 02:00 Sao Paulo time. Internal mode checks after its existing fast cycle. Manual checks share Mongo coordination and have a five-minute cooldown. Results are tenant-scoped in `section_association_meta`; 30 successful assessments are retained. After 36 hours, after an inventory revision, or after a failed latest attempt, current health is Unknown while the previous successful evidence remains available. The health diagnostic uses the existing service-account OAuth and shared rate limiter. It performs no course update; the native version-check POST is a read-only diagnostic. Both health routes require the verified LTI deployment, and manual requests also require same-origin request-integrity headers.

## Run

Use Node.js 22, install with `npm ci`, copy `.env.example` to `.env`, and provide credentials. Run `npm test` and `npm run check`; start with `npm start`. Keep dry-run enabled until logs confirm the expected targets. Set `SECTION_ASSOCIATION_FIX_DRY_RUN=false` only when ready to permit inactivation.

## Detailed audit exports

Each new automatic or manual execution stores verified Course Offering corrections and meaningful exceptions as separate records in MongoDB `section_association_audit`, linked by execution ID. The authenticated LTI history provides a per-execution Reports dropdown for Corrections CSV and Exceptions CSV when audit coverage is established; older runs show “Detailed reports unavailable.” The page-level action is labelled Export History CSV and exports every retained execution, including runs beyond the 50 displayed. Menus support keyboard dismissal and success feedback clears automatically. Expanded execution details use a compact strip with status-appropriate duration/count information. Corrections represent verified state changes; exception rows do not redefine the existing association-level error count. Audit rows are retained incrementally without an application TTL or count limit. Store initialization creates the audit retrieval and idempotency indexes; no migration or extra Brightspace lookup is required.
