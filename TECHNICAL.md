# Technical overview

## Components

`index.js` composes the web application, optional LTI provider, and trigger mode. `src/sectionAssociations/runtime.js` builds the OAuth service-account client, Mongo-backed rate-limited transport, store, reconciler, and service; the web and one-shot cron entrypoints share this runtime.

`client.js` contains bounded bookmark pagination and feature-specific API calls. `rules.js` enforces the association code and child suffix patterns. `resolver.js` validates every direct Group child and resolves exact Course Offering codes. `reconciler.js` validates every target before writes, then performs GET → full PUT → verification GET; only fully successful live reconciliations refresh the verified relationship snapshot. `store.js` tracks association metadata, child/target mapping snapshots, separate successful monitor timestamps, baseline audit state, successful full-discovery timestamps, and the shared worker lease. `service.js` handles time-windowed discovery, bounded rotating monitors, priority selection, and fast/recovery passes.

For scheduling, `client.js` accepts broad `I0001`/`ESPM-` queries or validated period-specific queries `{period}-I0001`/`ESPM-{period}-`; `config.js` parses and validates `SECTION_ASSOCIATION_DISCOVERY_PERIODS`, and `service.js` resolves the configured scope and coordinates full, fast, and maintenance-window selection. The service runs these additional requests sequentially and deduplicates by Org Unit ID. `store.js` performs batched discovery persistence and stores full-scan completion and recovery state. `cron.js` enforces the shared 50-item invocation limit, while `scheduler.js` provides internal timers; both use the same distributed lease.

The LTI provider is optional during bootstrap. Worker code uses only the Server-to-Server OAuth service account.

When configured, the LTI launch page offers administrator-only Run Now alongside its status/history views, and groups availability and worker state, shows the actual discovery period codes in bold or “All periods”, and presents latest date and outcome. It omits the latest Source field and suppresses a zero-work message that is already clear from the history counts. History replaces its visible source column with `Periods / Scope`, preserving source in storage and CSV. Rows display recorded scope; `Mixed` is appended when discovery ran with other activities. Historical-only and re-verification-only runs show their activity labels, while old or incomplete records without scope evidence show `—`. The six-column desktop table switches at 720px of history-container width to two-line rows, then at 560px to cards with date/outcome, scope, and a three-column counter grid. Viewport breakpoints at 860px and 620px provide fallback behavior. Date filters stack vertically within narrow history panels; Service Status also stacks when its own panel is narrow. Desktop execution summaries have 20px vertical padding. Expanded rows keep concise work information and duration or failure explanations, with scope already represented in the main row. Successful zero-work rows show “No work required” and duration. Run Now, Refresh, and Export History CSV remain available; the latter downloads all retained runs. Success feedback clears automatically, while errors remain announced accessibly. Execution IDs, coverage, and historical backlog stay in persisted summaries and CSV but are omitted from the page. Each request sends the launch-generated ltijs token in the `Authorization: Bearer` header and same-origin credentials. ltijs validates the token and session cookie before the route checks the verified deployment ID. The status endpoint reads the latest summary and latest 50 history documents from `section_association_meta`. Each execution is stored as a separate history document keyed by tenant and execution ID; upsert makes repeated writes with that ID idempotent. No history pruning or TTL is applied. The latest-summary document remains selected by start timestamp across sources. Automatic internal/cron and manual one-shot executions share the schema and history. `manualExecution.js` atomically accepts at most one outstanding tenant request, dispatches through `runSectionAssociationCron`, and exposes durable state. `cron.js` marks it running only after acquiring the shared lease, persists a manual-source execution summary and terminal request state, and recovers pending/interrupted requests on later automatic invocations. The web process polls every 30 seconds in both trigger modes. LTI POST authorization requires the validated session, deployment, same-origin request, and an explicit Administrator/SysAdmin role claim; the requester display name and a one-way subject hash are stored with the request and the execution summary for durable audit; status responses omit those identity fields. No separate queue, Render API call, or environment setting is introduced.

The history query index is `{ namespace: 1, history: 1, startedAt: -1, executionId: -1 }` and is created during store initialization. Existing data needs no migration; MongoDB creates the index on the next store initialization. CSV export streams all history documents through a cursor in batches of 500, formats the stored execution fields on demand, and does not create a permanent report. The CSV route uses the same LTI session and deployment verification as status. History consumes storage indefinitely until an operator applies normal MongoDB storage policies or capacity constraints; there is no application count limit or TTL.

The Execution History interface displays 50 records per page and queries MongoDB with `skip`/`limit` plus one lookahead record; ordering is `startedAt` descending and `executionId` descending. Optional From and To filters query `startedAt` directly using inclusive São Paulo calendar dates converted to local-midnight UTC boundaries. Filter changes return the interface to page 1. The status response includes `history.page` and `history.hasMore`; malformed pages/dates and reversed ranges receive HTTP 400. Export History CSV remains a separate cursor over all retained history, unaffected by page or date filters. Detailed report links remain attached to each displayed execution and work on every page. Pagination and filtering add no retention or deletion policy.

The summary contains a UUID, `source`, start/completion dates, final status, optional association-level counters and coverage metadata, plus optional `discoveryPeriods`, `discoveryActivities`, `monitoringPeriods`, and `monitoringActivities`. It records separate child/status checks attempted and succeeded, detected changes, mapping refreshes required, monitoring read errors, and current lag estimates. Lightweight reads are not counted as full reconciliations or verified corrections. Cron summaries combine evidence from their fast and recovery passes. Failed/incomplete runs retain only evidence collected before failure, and legacy documents are not backfilled. The history CSV appends period identifiers, activity labels, and monitoring counters after the existing columns; source and all previous fields retain their names and positions. Duration is calculated from the recorded start and finish times in the page. Expanded rows show the monitoring backlog for a child or status activity that ran; the separate historical coverage estimate remains available in persisted summaries and CSV export. The web process receives no external cron expression/timezone, so next execution is reported unavailable. Summary-write failures are safely logged. Current worker activity comes from the in-process scheduler or shared cron lease. Run Now uses the existing reconciler and safety checks; the UI exposes no direct corrective operation outside that worker.

## Reconciliation algorithm

1. Require association Course Offering type and either legacy code `^\\d{6}-\\d{2}-\\d{4}-I0001$` or PeopleSoft shape `ESPM-{valid YY01/YY02 period}-{nonblank remainder}`. Session and sequence values are not fixed.
2. Read bounded child pages. Require at least one child; every child must be Type `Group` and end with `-\\d{5}`.
3. Derive each original Course Offering code by removing the five-digit child suffix; reject duplicate derived codes.
4. Resolve every derived code exactly once and require a distinct Course Offering ID.
5. GET and validate all current targets and build safe full update payloads before the first write.
6. Leave inactive targets unchanged. In dry-run report active targets and keep the association pending. In live mode re-read each active target immediately before PUT, change only `IsActive`, then read back and verify.
7. Mark complete only after every target is confirmed inactive. Store `lastReconciledAt`, `lastVerifiedAt`, and `reconciliationVersion` as positive evidence. Block validation failures; leave transient/uncertain work retryable.

The PUT body preserves all current Course Offering fields and converts Brightspace RichText Description to RichTextInput. An uncertain PUT is read back and never blindly replayed.

## Baseline, eligibility, and scheduling

`SECTION_ASSOCIATION_DISCOVERY_PERIODS` is optional. An undefined value, explicitly empty value, or case-insensitive `auto` uses `Intl.DateTimeFormat` in `America/Sao_Paulo` to resolve previous/current/next. January–June maps to `YY01`, July–December to `YY02`; previous and next roll across years. October 2026 resolves to `2601`, `2602`, `2701`; February 2027 to `2602`, `2701`, `2702`; August 2027 to `2701`, `2702`, `2801`. A comma-separated list (for example `2601,2602,2701`) selects exactly those discovery periods after trimming and deduplication; a single period such as `2701` is also valid. `all` schedules the broad pair once daily instead of period-specific daytime association searches; ongoing child monitoring remains limited to previous/current/next. Keywords are case-insensitive, and malformed values fail startup. Period configuration selects Brightspace offerings to query; it does not restore an association that a failed IPSIS import never created.

Auto and explicit fast passes make a fully paginated Brightspace request for each selected period:

```text
GET /d2l/api/lp/{version}/orgstructure/?orgUnitType=3&orgUnitCode={period}-I0001
GET /d2l/api/lp/{version}/orgstructure/?orgUnitType=3&orgUnitCode=ESPM-{period}-
```

The two broad queries, `orgUnitCode=I0001` and `orgUnitCode=ESPM-`, are fully paginated and cover historical and future periods. Initial baseline and subsequent daily full scans begin on the first cron execution at or after 23:00 local time and may retry through 00:45. A successful pair is timestamped in tenant-scoped `section_association_meta` only after both queries and records persist. If either query fails, its timestamp stays unchanged and later executions through 01:00 retry in the same nightly window; after the window it remains due until the next nightly window. Period queries run only from 07:00 to 23:00. Mongo persistence failures fail the cycle and do not mark completion. `all` uses the daily broad pair.

The first successful full discovery uses a Mongo baseline lease and marks associations already present as `baseline: true` for audit. Baseline does not suppress reconciliation. Historical and new associations go through the same reconciler; historical work has no new-association stability delay. New associations wait the configured stability duration.

Each scheduled run processes at most `SECTION_ASSOCIATION_FIX_MAX_RECONCILIATIONS_PER_RUN` (default 50) full reconciliations. Cron passes the fast result into its due recovery pass; both share the 50-item limit. Pending and blocked work remains eligible 24 hours a day. Completed-association optimization is handled by distinct bounded paths: child checks from 07:00–23:00 and cached-ID status reads every 30 minutes from 01:00 through 06:30 (window 01:00–07:00). Child checks default to 125 associations and status checks to 150 per eligible invocation. The separate configuration variables can reduce those caps. Both query the tenant-scoped Mongo population, order by oldest successful check, and retain overflow for later runs. The child-monitoring backlog counts successful-inspection timestamps before the current hourly marker and does not apply the one-hour recent-attempt selection cutoff, so it can include temporarily cooling-down records. Recent failed attempts back off for one hour. All reads use the shared Brightspace rate limiter.

Cron mode runs one bounded fast pass per external invocation and uses persisted `lastRecoveryAt` to keep the four-hour pending/blocked recovery schedule independent. The recovery pass reuses the fast pass's discovery and consumes only the remaining part of the shared 50-reconciliation limit. Internal mode runs immediate and recurring fast/recovery timers through the same service functions. Both modes acquire and renew the same namespaced Mongo worker lease and await release; this prevents overlapping scans and reconciliation across cron/internal instances, with lease expiry providing crash recovery.

Successful reconciliations store `verifiedChildren` (direct Group IDs/Org Codes), `verifiedTargets` (original Course Offering IDs/Org Codes), paired `verifiedMappings`, `verifiedMappingVersion`, `lastSuccessfulChildInspectionAt`, and `lastSuccessfulStatusVerificationAt` in the existing `section_associations` document. The mapping is written only after full validation and all originals are confirmed inactive. Dry-run with any active original remains pending and cannot replace the snapshot. Legacy completed rows lacking mapping version are selected for full reconciliation before optimized monitoring.

Daytime monitoring fetches direct children and normalizes both persisted `{id, code}` snapshots and Brightspace rows (`Identifier` or `OrgUnitId`, plus `Code`) into sorted `{id, code}` rows. It detects additions, removals, and changed identities without treating response reordering as a change; current child types are independently required to be `Group`. A changed snapshot schedules full reconciliation within the remaining 50-item allowance; unused/overflow items remain due. Removed sections never cause reactivation. Nighttime verification GETs each saved original ID and validates its ID, Course Offering type, Org Code, and inactive state. All inactive results advance only the status timestamp. Active, missing, or inconsistent results trigger full association/children/exact-code validation before the existing reconciler can write. API failures leave the prior verified timestamps and mappings intact. Fresh success timestamps are separate for child checks and status checks because neither read establishes the other's evidence. These phases add report counters and lag values without changing correction or error aggregation semantics.

For temporary investigation, `SECTION_ASSOCIATION_DEBUG_ID` enables one structured child-monitoring diagnostic for the matching numeric association ID, or `sample` logs the first association inspected by daytime child monitoring in each execution. It reports the saved/current child ID and Org Code rows, current child types, mapping validation result and reason, normalized-list comparison, reconciliation reason, capacity disposition, and successful-inspection timestamp outcome. It reuses data already read by the worker and does not add MongoDB or Brightspace reads or change processing. The setting is unset by default and must be removed after troubleshooting.

The daily schedule is: 23:00–01:00 one broad-discovery window (including 00:00–00:45 retries if needed); 01:00–07:00 cached status verification at :00 and :30, with pending/recovery work at intervening quarter-hour cron ticks; 07:00–23:00 configured period discovery (unless scope is `all`) plus child monitoring; pending/blocked recovery remains eligible continuously. No additional Render job or timezone setting is required, and automatic period rollover needs no manual maintenance.

```mermaid
flowchart TD
  A[15-minute cron, 24/7] --> B{São Paulo window}
  B -- 07:00–23:00 --> C[Period discovery, then child monitoring]
  B -- 23:00–01:00 --> D[Retry broad I0001 and ESPM scans until success, once per nightly window]
  B -- 01:00–07:00 at :00/:30 --> E[Cached original status verification]
  B -- intervening :15/:45 ticks --> F[Pending/recovery work continues]
  C --> G[New/pending work before monitoring-triggered reconciliation]
  D --> H[Persist discovered IDs and baseline]
  E --> I[Fresh full reconciliation for active or untrusted targets]
  G --> J[Recover pending/blocked work when due; full reconciliations max 50]
  H --> J
  I --> J
```

## Persistence

`section_associations` is keyed by tenant namespace and `associationOrgUnitId`. It stores association code, first/last seen and checked times, status, audit baseline marker, safe errors, compact outcomes, and positive verification evidence. `section_association_meta` stores baseline coordination, cron lease/recovery metadata, and the last successful broad discovery timestamp. Mongo is an operational work ledger; current Brightspace records remain authoritative.

After the baseline is ready, discovery deduplicates valid association IDs and compares them with Mongo in tenant-scoped `$in` queries of at most 500 IDs, supported by the existing unique `{ namespace: 1, associationOrgUnitId: 1 }` index. Known records receive a bounded bulk refresh of `associationCode` and discovery-only `lastSeenAt`; inserts are limited to IDs absent from the comparison and use bounded unordered bulk upserts with `$setOnInsert`, preserving existing state, first-seen time, baseline marker, and reconciliation evidence. Reconciliation updates `lastCheckedAt` but never `lastSeenAt`. Duplicate-key races are confirmed against Mongo and counted as already known. Initial baseline writes are chunked to the same bound and still mark only inserted records as baseline. Counters count distinct valid discovered IDs. A partial bulk failure fails the execution so it cannot be reported as complete; already-applied operations are safe to observe on the next cycle.

A 404 from the initial association-detail GET sets `missingObservedAt` once and leaves the association pending. `confirmMissing` scans candidates in bounded batches; it changes a record to `missing` only when a successful fresh discovery finishes at least 30 minutes after that observation and the exact D2L ID is absent. Period queries filter by both stored family and academic period; broad `I0001` coverage checks only legacy records and broad `ESPM-` coverage checks only PeopleSoft records. The service supplies IDs from the just-completed raw discovery response, including returned IDs that no longer pass association validation, so matching Org Codes cannot substitute for ID evidence. Failed or incomplete queries never invoke confirmation for their coverage. No discovery result sets are persisted and no Recycle Bin endpoint is called. `missing` is not a completed/blocked state and is excluded from fast/recovery selectors and backlog counts. Positive discovery of the same ID restores it to `pending`, clears observation/confirmation metadata, and preserves its history; another ID with the same Org Code is inserted independently. Confirmation writes a `missing-confirmed` exception audit row and structured log event, but does not increment completed or correction counters. Legacy documents without missing metadata remain unchanged and need no migration.

## Transport and write boundary

JWT exchange is shared with the application. Brightspace URLs remain HTTPS on the configured origin; redirects are disabled, request timeouts are bounded, API traffic passes through the shared rate gate, and errors omit credentials. The feature's only write is a narrowly scoped Course Offering PUT.

## Detailed execution audit

Daytime child monitoring reuses the verified child snapshot and current child response. It normalizes and sorts `{ id, code }` rows and compares by child ID: unseen IDs are additions, absent IDs are removals, and same-ID code changes are reported. Response ordering is ignored, and invalid/missing saved mappings do not produce before/after rows. Discovery and baseline do not create child-change records.

For each genuine change, the first observing execution owns an immutable `child-change` detection audit row. Before inserting it, the association document stores the unresolved change, signature, detection timestamp, source, execution ID, and stable record key. This ordering lets a later inspection restore the same detection row after a failure between writes. Repeated observations reuse unresolved rows, avoiding duplicate detections. When reconciliation later reaches a terminal result, a separate `reconciliation-outcome` audit row is written under the execution that performed that work, with the original detection execution/key. Detection rows keep their original pending/deferred outcome. Completed reconciliation clears the unresolved association links; blocked/failed work remains linked for a later retry. Outcome rows contain only related offering IDs/codes established from the verified prior mapping or reconciliation result. Removal records preserve the former child ID/code and never cause reactivation.

Child Changes CSV fields, in order, are Detection date/time, Outcome date/time, Execution ID, Execution source, Audit event, Detection Execution ID, Detection Record Key, Parent Section Association D2L ID, Parent Section Association Org Code, Change type, Child Section D2L ID, Previous Child Section Org Code, Current Child Section Org Code, Related Original Course Offering D2L ID, Related Original Course Offering Org Code, and Reconciliation outcome. The CSV endpoint uses the existing tenant namespace, execution ID, verified LTI session/deployment authorization, stream/cursor flow, CSV quoting, and formula-injection protection. Empty reports contain headers and require no Brightspace request.

Each scheduled or manual execution passes its UUID and source into the shared reconciler. After a PUT is verified inactive, it upserts one `correction` record into `section_association_audit`; the stable key is execution, parent association, and target offering. Validation blocks, update failures, verification failures, and unexpected association failures produce deduplicated `exception` records with sanitized explanations. Corrections are target-level; the existing `correctionsApplied` value remains association-level (at least one verified target update). Audit write failures mark execution detail coverage incomplete, and completed writes remain persisted if a later operation fails.

The audit collection has a unique `{ namespace: 1, executionId: 1, kind: 1, recordKey: 1 }` index and an execution retrieval `{ namespace: 1, executionId: 1, kind: 1 }` index, created at store initialization. LTI Corrections CSV, Exceptions CSV, and Child Changes CSV endpoints require the same verified session and deployment check as history export. They stream rows from Mongo on demand, safely escape CSV/formula content, and make no Brightspace calls. Empty reports have headers. Only summaries marked `detailedAuditAvailable` show report actions; older executions without that marker are explicitly unavailable, not treated as zero. No TTL or application retention cap is applied; storage follows MongoDB capacity and operator policy. No migration is required.

Reconciliation diagnostics use stages `association-read`, `children-read`, `exact-code-lookup`, `target-read`, `target-update`, and `verification-read`. A Brightspace HTTP failure retains its status; known timeout/network errors and OAuth failures use separate stable reasons without inventing a status. Render reconciliation failure lines include the stage, safe API endpoint identifier, reason, and available status. Exception rows classify failures as `read-failed`, `update-failed`, `verification-failed`, `validation-blocked`, or `processing-error`; explanations identify the failed operation and include the known HTTP status and target Org Code/ID. Available association and target names are stored from already-read records. No additional Brightspace calls are made for diagnostics. Operators use the execution's Exceptions CSV; expanded history rows continue to display the existing persisted run summary explanation.

## API Health Check

`apiHealthInventory.js` is the dated source of truth for six logical operations in `client.js`. Discovery and exact-code resolution share the Org Unit list route but have distinct purposes and query parameters; Course Offering GET and PUT remain distinct methods. The OAuth service-account token exchange is separately recorded as an authentication diagnostic sourced from `BS_OAUTH2_TOKEN_ENDPOINT`, not a versioned LP/LE operation. The automated inventory test executes every client method and compares normalized method/route shapes, including the discovery query distinctions.

The current evidence verification date is 2026-10-19. The official D2L lifecycle page lists LP 1.49 as oldest fully supported, LP 1.46–1.48 as deprecated, and LP 1.45 and older as obsolete. It documents LP 1.49+ route support for these Org Unit and Course Offering calls. The Course Offering update has an additional endpoint contract constraint: `IsActive` is required from LP 1.59 and unsupported earlier, so 1.59 is recorded as the minimum for the application's update operation. Minimum versions are stored per endpoint; do not generalize them to unrelated routes. Lifecycle evidence becomes stale after 90 days and is then Unknown until the inventory evidence date and source are reviewed. The inventory provides official D2L resource, routing, API properties, and version lifecycle links.

`apiHealth.js` uses the existing service-account OAuth, `createBrightspaceGet`, and Mongo-backed rate-limited HTTP client. Each assessment validates `GET /d2l/api/lp/versions/` and `POST /d2l/api/versions/check`; neither call performs a Course Offering mutation. Version health is calculated from configured version, the tenant's supported list/check response, local lifecycle evidence, and each operation's verified minimum. Unsupported or below-minimum versions are Critical, obsolete versions are Critical, deprecated versions are At Risk, lower-but-supported versions are Update Available, and current supported versions are Healthy. Missing or stale evidence yields Unknown. Contract Verification remains a separate `Not Verified` field because checking tenant version support does not exercise every endpoint payload or response contract.

The service stores current state and the last successful result in a tenant-namespaced `section_association_meta` document. It keeps last-attempt status and sanitized error code/status even on failure and appends successful assessments to a 30-entry bounded history. A Mongo lease coordinates manual and automatic checks; manual requests also atomically reserve the five-minute cooldown. Failed attempts preserve the previous result but set current health to Unknown. Cached state is stale after 36 hours or an inventory revision change and returns Unknown endpoint counts until a current assessment succeeds.

Cron mode starts a due check at the end of the existing invocation, after reconciliation and maintenance-summary persistence finish. Internal mode checks after the existing fast tick and its summary are saved. These checks cannot fail or change reconciliation status, counters, or elapsed summaries, and they run after operational API work so they do not contend for the shared Brightspace rate limiter during reconciliation. Due checks run once per Sao Paulo calendar day after 02:00; no Render job or interval is added. Manual requests call the same service and Mongo lease. The LTI GET route only reads Mongo; the POST route verifies the LTI token's configured deployment, then requires an HTTPS same-origin `Origin`, same-origin Fetch Metadata when present, and `X-Requested-With: XMLHttpRequest`. Both routes disable caching. No token, private key, raw header, or request URL is persisted.

If a Brightspace endpoint, method, configured version source, OAuth scope, or contract changes, update the inventory, its source-coverage and assessment tests, and the operating documentation. Do not treat the endpoint `contractVerification` label as proof of a live contract test.


## Monitoring details and verified mappings

Execution History stores the child and cached-status monitoring counters returned by the worker, including successful/attempted checks, detected changes, mapping refreshes, and due backlog. The expanded row renders metrics only when the corresponding activity flag is present, so historical executions without these fields remain unchanged. A completed dry run can persist a reusable mapping only after fresh association, child, exact-code, and target reads confirm all targets are already inactive; a dry run with any active target remains pending. This prevents completed dry-run records from repeatedly entering full reconciliation solely because their mapping was omitted.
